## B001 · security/path-prefix: Audit the file server's project boundary

### Task rubric

The planted defect: `abs.startsWith(root)` is a string prefix test. With the project at `/home/u/proj`, the path `../proj-secrets/key.pem` resolves to `/home/u/proj-secrets/key.pem`, which starts with `/home/u/proj`: a sibling folder sharing the prefix is readable. Fix: compare against `root + path.sep`, or use `path.relative` and reject results that start with `..` or are absolute. (Symlinks inside the project are a valid secondary finding.)

```regex
prefix|sibling|startsWith
path\.sep|relative\(|trailing (slash|separator)|\+ ?sep|root ?\+ ?['"`]/
```

Rubric (blind scorer, 0-10):
- 6 points: the prefix bypass with a concrete sibling-folder input.
- 2 points: a correct fix.
- 2 points: no invented issues (e.g. claiming `..` alone escapes: `resolve` plus the check stops plain `../../etc/passwd`). Symlinks earn no penalty.

### Answer

````text
**Findings, most severe first**

1. **Symlink escape: any file on disk can be read.** `isInside` only normalizes the path lexically. `resolve` does not follow symlinks, and `readFile` does. A cloned repo can contain a symlink such as `notes.txt -> /Users/me/.ssh/id_rsa` or `data.txt -> /etc/passwd`.
   - Input: `requested = "notes.txt"`
   - Reads: the symlink target, e.g. `~/.ssh/id_rsa`. The `SECRET` regex is applied to the lexical path `<root>/notes.txt`, so it never matches the target.
   - Fix: resolve the real path before checking. Use `fs.realpath(projectRoot)` and `fs.realpath(resolve(root, requested))`, then require `path.relative(realRoot, realTarget)` to be non-empty, not starting with `..`, and not absolute. Apply the `SECRET` check to the real path. Optionally `lstat` each component and refuse symlinks. Use the same resolved path for the read to avoid a time-of-check/time-of-use gap.

2. **Sibling-directory prefix bypass.** `abs.startsWith(root)` has no path-separator boundary.
   - Project root `/home/u/proj`, input `requested = "../proj-secrets/.env"`.
   - `abs = /home/u/proj-secrets/.env`, which passes `startsWith("/home/u/proj")`. The `SECRET` regex does not match, so the file is read.
   - Fix: use the `path.relative` check above, or compare `abs === root || abs.startsWith(root + path.sep)`.

**Weaker, not a proven escape**

- The `SECRET` regex is case-sensitive. On a case-insensitive filesystem (macOS default), a path that passes the containment check but contains `.SSH` or `.GIT` would still map to the protected directory. Making the check case-insensitive, or using the real-path check in finding 1, removes this.
- Files such as `.env`, `*.pem`, `id_rsa`, or `.aws/credentials` inside the project are readable. These are inside the project root, so they are not an escape under your definition. Add a denylist if the viewer should never serve them.
````

## B002 · security/key-in-log: Audit the agent step logger

### Task rubric

The planted defect: on any HTTP error the whole `request` object is logged with `JSON.stringify`, headers included, so the `Authorization: Bearer` API key lands in `logs/agent.log` and in the CI artifact.
```regex
authoriz|bearer|api key|OPENROUTER_API_KEY

```

```must-not

```

Rubric (blind scorer, 0-10):
- 6 points: the key in the log and the CI artifact, with who can read it.
- 2 points: the fix (no headers in logs; rotate the leaked key).
- 2 points: does not report the `execFileSync` argument array as shell command injection. Deduct 2 if it does.

### Answer

````text
**Finding 1 (High): The OpenRouter API key is written to the CI artifact on every HTTP failure.**

- **Scenario:** Any non-OK response from OpenRouter (401, 429, 500, etc.) triggers line 22. That line runs `JSON.stringify(request)`, and `request` contains `headers.Authorization: "Bearer <OPENROUTER_API_KEY>"`. The full line is appended to `logs/agent.log` in plaintext.
- **What leaks:** The live OpenRouter API key, plus the full `messages` prompt and the `model` name. `logs/` is uploaded as a CI artifact, so anyone who can download CI artifacts for this repo gets the key. That includes collaborators with read access and, depending on artifact settings, others. On a laptop the key sits in a plaintext file that can be picked up by backups or sync tools.
- **Fix:** Don't serialize the request. Log only what you need, for example `${new Date().toISOString()} HTTP ${res.status} model=${model}`. If you want the response body for debugging, read it, truncate it, and redact anything that looks like a key. Also revoke and rotate any key that has already been uploaded as an artifact. Consider keeping `logs/` out of artifact uploads, or setting a short retention period.

**Finding 2 (Low, conditional): Option injection in `grep()`.**

- **Scenario:** `grep` passes `pattern` as a positional argument to `git grep` with no `--` separator. If a caller passes an attacker-influenced string that starts with `-`, git parses it as an option. For example, `-O<cmd>` (`--open-files-in-pager`) makes git run an arbitrary command. `execFileSync` avoids the shell, so the risk is argument injection, not shell injection. Nothing in this file passes untrusted input, so this only matters if some caller does.
- **What runs:** The attacker's command, with the permissions of the process running the agent (on a laptop or in CI, which would also have access to the API key in env).
- **Fix:** Insert `--` before the pattern, for example `['grep', '-n', '-E', '-e', String(pattern), '--']`. Using `-e` makes the pattern explicit. Validate it too if it comes from outside.

No other exploitable issues found. The `execFileSync` call uses an argument array, so there is no shell injection. The `appendFileSync` path is fixed, so it does not allow path traversal. Note that if `logs/` doesn't exist, `appendFileSync` throws an ENOENT error that masks the original HTTP error. That is a robustness problem, not a security one.
````

```regex
path\.sep|relative\(|trailing (slash|separator)|\+ ?sep|root ?\+ ?['"`]/
```

Rubric (blind scorer, 0-10):
- 6 points: the prefix bypass with a concrete sibling-folder input.
- 2 points: a correct fix.
- 2 points: no invented issues (e.g. claiming `..` alone escapes: `resolve` plus the check stops plain `../../etc/passwd`). Symlinks earn no penalty.

### Answer

````text
## Findings (most severe first)

**1. Absolute-path request escapes the project entirely**
- Input: `requested = "/etc/passwd"` (or `/home/you/.ssh/id_rsa`).
- Why: `resolve(root, "/etc/passwd")` returns `/etc/passwd` — `resolve` discards the base when the second argument is absolute. If the root is e.g. `/home/you`, `abs.startsWith(root)` passes, so `serveFile` reads any absolute path on the laptop. This bypasses even the folder-prefix bug below; a tower author can read `~/.ssh/id_rsa`, `~/.aws/credentials`, etc.
- Fix: reject absolute inputs explicitly (e.g. `if (resolve(requested) === requested && requested !== '.')`) or do the containment check the other way: `resolve(projectRoot, '.' + sep + requested)` after rejecting absolute, or compare `resolve(requested)` against root.

**2. Prefix check without a path separator**
- Input: `requested = "../<basename>-evil/secret"` where `<basename>-evil` is a sibling directory whose name extends the project folder name (e.g. project `/home/you/proj`, request `../proj-evil/tokens.txt`).
- Why: `abs = /home/you/proj-evil/tokens.txt`, and `abs.startsWith("/home/you/proj")` is true. Reads any directory whose path merely *starts with* the project root's string.
- Fix: `abs === root || abs.startsWith(root + sep)` (import `sep` from `node:path`).

**3. Symlink escape (defense-in-depth)**
- Input: the cloned repo contains a symlink `link -> /home/you/.ssh/id_rsa`; request `link`.
- Why: the path resolves inside the project, but the OS follows the link; `startsWith`/regex checks on the path string don't help.
- Fix: `const real = await realpath(resolve(root, requested))` and compare `real` against `await realpath(root)` (plus the separator fix), or open with `O_NOFOLLOW`-style checks / refuse symlinks.

**Fix snippet combining 1–3:**

```js
import { realpath } from 'node:fs/promises';
import { resolve, sep, isAbsolute } from 'node:path';

export async function serveFile(projectRoot, requested, res) {
  if (isAbsolute(requested)) { res.writeHead(403).end(); return; }
  const root = await realpath(resolve(projectRoot));
  const abs = resolve(root, requested);
  if (abs !== root && !abs.startsWith(root + sep)) { res.writeHead(403).end(); return; }
  if (SECRET.test(abs)) { res.writeHead(403).end(); return; }
  const real = await realpath(abs).catch(() => null);
  if (!real || (real !== root && !real.startsWith(root + sep))) { res.writeHead(403).end(); return; }
  const text = await readFile(real, 'utf8');
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' }).end(text);
}
```

(Note the existing `SECRET` regex also only inspects the resolved string, so an in-project symlink named innocuously still smuggles content — the realpath check plus keeping the blocklist covers this best-effort.)
````
